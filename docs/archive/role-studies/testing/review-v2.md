## 首轮审查结论

1. 当前 AC-01—AC-42 共 42 项，覆盖计时、恢复、托盘、Hyper-V、数据、资源和集成。它们目前都标记待执行，缺少实现后的证据。
2. 当前 `docs/design.md` 明确保留 280×220 主卡、200×64 mini、默认深色以及部分点击热区依附文字。`docs/ui-revision-v2.md` 已明确覆盖固定尺寸和默认深色，并要求同宽、浅深主题、圆圈和按钮全热区。新版设计尚未出现在基线文档中，因此新版画板需要独立验收并建立追踪项。
3. `docs/acceptance.md` 的 42 项里没有专门验证系统主题初始查询/查询失败/运行时切换、显示器物理宽度 10% 的换算、展开收起同宽、圆圈状态语义、按钮文字居中或整块按钮热区。AC-17/18 覆盖一般多屏和 DPI 场景；测试还需对四项 UI 要求逐项断言。
4. UI v2 对“圆圈表达 remaining / target”给出方向，但圆弧起始角、顺逆时针、completed/idle/recovery 的视觉、色彩对比目标、辅助技术的动态播报策略仍待产品与设计冻结。测试以这些字段为原型评审阻塞项。
5. 10% 尺寸应同时记录当前窗口中心所在显示器、物理宽度、DPI、缩放因子、物理像素目标及逻辑像素结果；显示器切换后重算，并按工作区修正位置。验收不引入自定最小/最大宽度。计算示例：1366@100%=137 px；1920@100%=192 px；2560@125%=round(256)/1.25=204.8 DIP；3840@150%=round(384)/1.5=256 DIP。最终舍入规则和 API 获取口径待窗口适配方案冻结。

- 发现 X1（P1，需冻结口径）：产品 v0.2 第 2 节仅写 `round`，并称半值规则待统一；窗口契约“单位与公式”段选择 `round_half_up`。需产品和架构评审将半值规则写回产品规格，并明确最终投影到 OS 整数窗口像素时的舍入顺序。建议测值包含显示器宽度除以 10 恰为 x.5，以及 Wdip 投影为 x.5 的情况，逐层记录期望值。
- 发现 X2（P1，事件时序未完全闭合）：窗口契约同时把 DPI 改变、显示配置改变和主题颜色改变列为平台事件；`GeometryChanged` 依赖完整快照，`DpiChanged` 带旧/新 DPI 和建议矩形，`DisplayTopologyChanged` 延迟至下一 UI tick 合并枚举。产品规格只要求重新读取屏幕和 DPI 并重算。需冻结 DPI 消息、拓扑变化、中心点变化的顺序和合并规则，尤其中心点仍位于旧屏/新屏边界时，以哪一次 GeometrySnapshot 更新宽度；显示器失效时如何避免使用过期建议矩形。
- 发现 X3（P2，名词口径）：产品表写逻辑单位 `dip`，窗口契约在事件字段中混用 `physical_rect_px`、`dpi_x/y` 与 Slint DIP；契约说明转换只在布局边界执行一次。需在数据结构上标注坐标空间（屏幕物理像素/窗口逻辑 DIP），测试同时采集真实窗口物理外框和逻辑宽度，防止虚拟化坐标误作面板物理像素。
- 发现 X4（P2，分支引用）：产品表正式新增 ID 为 AC-43—46；当前基线 `docs/acceptance.md` 仍止于 AC-42。本测试计划的 UI-01—07 是测试细分编号，不替代 AC ID。产品/Lead 更新正式验收快照时应保留 AC-43—46 主追踪，并把 UI-01—07 和 W-01—07 作为覆盖子用例链接，避免同一需求分成相互冲突的预期。

### 接口一致性观察

- **TimerSnapshot / revision：** 计时提案使用全局状态 revision、`expected_revision` 和 `command_id`；数据库提案以 `schema_meta.state_revision` 支持 idle/completed 转换，并要求活动行 revision 与全局 revision 对齐；恢复、托盘、前端均消费同一 Snapshot/revision。总体模型一致。待冻结 `settings.revision` 与 `state_revision` 的作用域，另外明确 Tick 的只读快照是否增加版本，以及 idle/completed 时 Snapshot 如何从空活动行和最近历史组合。
- **CAS 与去重：** 计时/恢复候选与数据库事务规则相符：检查 command receipt、expected revision，再原子更新活动快照、终态历史和 receipt，提交后发布；陈旧 checkpoint 被 CAS 拒绝。命令 receipt 保留期限和 checkpoint 是否使用 command receipt 仍待数据库/Lead 冻结。
- **暂停、恢复与时间：** 计时的 `active_ms` 截止值、暂停冻结 remaining、恢复建立新截止值，与恢复提案的 suspend→recovery、重启不复用单调时钟、continue/keep_paused/discard 均一致。15 秒 checkpoint 为共同目标；应把它标记为目标并在恢复故障注入记录存储失败期间的实际损失，而非将周期目标表述为已验证上界。
- **单实例和生命周期：** 托盘提案的每用户互斥量 + 当前用户 named pipe 激活，与数据库至多一条活动 session、CAS 共同保护单实例和单活动段。接口仍需冻结 mutex 命名/生命周期、SID ACL、启动竞争、管道失败时第二实例退出反馈，以及退出清理与 event loop 的精确回执顺序。
- **统计：** 统计服务将 focus `interrupted` 的实际活动毫秒计入实际专注时间，而 completed focus 才增加完成轮次；日期依开始时 `start_local_date`。数据库/数据管理的日期、偏移、终态和毫秒字段大体兼容；但数据库提案有一处冲突，见 X5。
- **导出与永久清除：** 数据管理定义版本化 JSON、固定 CSV 列、备份先行清历史、永久清除移除应用管理备份并保留用户外部导出文件；数据库 Repository 提供一致快照、备份校验、清历史和 clear_all 原子接口，主方向一致。用户是否可选择 JSON 包含设置/活动快照、CSV BOM、导出日期边界和清理确认/活动段结束顺序仍待产品冻结。
- **前端 / UI 追踪：** 前端 Geometry、Theme、TimerSnapshot、控件热区和辅助技术字段与既有 UI-01—07 相符。前端将 idle 无目标圆圈描述为静态空闲态，计时提案允许隐藏或全空、窗口契约另待设计；产品 AC-43 的用例没有 idle，需将 idle 视觉与可访问语义纳入设计冻结和测试覆盖。
