# 任务、上下文与并行协作调整提案

状态：组织与上下文管理方案已获用户批准并实施；历史session、分支与工作树以可恢复方式保留。代码模块与具体业务接口仍为候选，本方案保持业务开发、架构审批、PR合并和发布门槛。执行结果见[整理记录](cleanup-report.md)。

## 判断

Lead协调、多个独立session执行、Git Worktree隔离改动的组合适合本项目。需要调整的是任务边界、上下文输入和任务生命周期。上一轮按岗位清单创建11个长期角色session，细分了代码改动却重复了公共协议的设计责任；运维诊断也进入了业务设计会话。

实际审查证据包括：统计与数据库首稿的actual_focus_ms口径冲突；多个角色重复描述revision、Snapshot和保存顺序；数据删除确认与结束活动段的顺序分散在数据和数据库提案中。见team/testing-v2分支的docs/team/testing/review-v2.md及相应角色提交。当前尚无Rust/Slint业务代码，组织调整可以先于实现落地。

## 四类对象分开管理

| 对象 | 职责 | 生命周期 |
| --- | --- | --- |
| 模块 | 稳定的代码/数据边界、依赖与维护责任 | 跨任务保留 |
| 任务 | 一个可验收交付物、明确输入/排除范围/完成条件 | 从Ready到验收关闭 |
| Session | 执行一个任务或审查一组紧密相关改动的上下文 | 完成任务并交接后结束本轮 |
| Worktree/分支 | 承载一项独立代码变更或PR，隔离文件、索引和HEAD | 变更评审/集成完成后归档 |

模块负责人是持续的责任，执行任务使用短会话。同一模块下一项独立任务可开启新的session，按版本化资料交接。Worktree负责文件改动隔离；干净上下文由任务输入范围和session生命周期维护。一次只读审查可以直接读取指定提交，无需复制一套工作树；可编辑设计/代码任务使用独立工作树。

取消统计、恢复、托盘、数据库等细项的永久session配额。它们仍是可单独建Issue的功能，任务满足独立输入和验收条件时再拆开执行。新增的是明确的应用集成责任，以及按里程碑启用的构建/发布任务；当前阶段无需常驻发布Agent。

产品/设计与视图在职责上分开，前者的Figma工具轨迹不进入后者的实现上下文。独立Reviewer先读验收标准和实际diff/原型，再按需要看作者理由。

## 候选代码边界

当前为目录提案，不创建业务源码。首版采用单个Windows桌面程序，代码可按以下逻辑划分：

- domain：纯计时、阶段/轮次与状态规则，注入时钟。
- application：协调命令、候选状态、存储回执与effects；负责恢复、退出和数据管理流程。
- platform/windows：原生窗口、主题/DPI、托盘、单实例及系统事件。
- storage：SQLite schema、Repository、迁移与查询。
- ui：Slint视图、控件、语义主题及布局。

domain与application可由同一执行分组维护，但保留纯内核与副作用协调的代码边界。指标含义由产品定义，应用层调用，存储层按契约查询。跨层状态转换由application统一排序，禁止各层自行维护第二份计时状态。

## 任务拆分与并行准入

一个任务满足以下条件再进入Doing：

1. 有明确交付物和完成条件，完成后可停止本session。
2. 上游输入有已批准版本或具体commit SHA，待裁决接口先标依赖。
3. 有独占写入范围；跨模块变更由Lead指定单一主责。
4. 有可独立执行的验证方法，集成测试责任另行标明。

两个任务可以并行的条件是输入稳定、写入范围分开，且各自能独立验收。调用不同工具的研究任务可并行；共同修改同一事件循环、协调器或schema的任务按依赖推进。

建议开发期从3个实现任务并行起步，另按需运行1个独立审查任务。记录接口等待、返工、冲突与review积压，再决定增减并发。项目历史可以保留很多session，活跃写入任务保持有限。

## 当前阶段与首轮开发顺序

设计确认前，主要活跃任务为：产品澄清剩余行为、设计完成新版原型、独立审查；其他模块首轮提案汇总成一个接口评审包，结束无依赖进展的重复规划。

用户批准设计和关键架构后：

1. 建立可运行基线与公共契约，确认Command、TimerSnapshot、Geometry/Theme、Repository和数据版本边界。公共Cargo/构建入口指定单一写入者。
2. 从同一集成基线并行实施：计时/应用核心、最小Windows Shell、Slint视图（使用同版本fixture）。存储可以在核心协议稳定后接入并替换mock；写入任务数量按实际依赖排队。
3. 集成最短端到端流程：开始→暂停→恢复→到期→保存→重启恢复。独立验证真实应用行为，再扩展托盘、DPI/主题、数据管理和统计等特性。
4. 每个后续Issue对应一个完整可验证的用户结果；必要时设2—3个依赖子任务。模块方案文档完成与用户功能交付分别登记。

## 每个执行session的最小交接包

Lead提供一份任务说明，包含：目标、排除范围、已批准需求/原型版本、起始commit、接口版本、允许写入路径、验收命令/步骤、依赖与停止条件。默认从全新上下文启动，不传整段上游聊天或全部角色研究记录。

开工必读：短AGENTS导航、当前任务说明、直接相关的接口/代码/测试。其他资料按索引检索。设计任务读取布局/主题与相关状态；数据库任务读取schema/Repository/故障语义；计时任务读取状态机/时钟/命令。跨模块资料只给接口边界和少量示例。

交付包包含：commit/PR、实际修改范围、执行过的验证和结果、未决问题、下游需要知道的接口变化。详细工具轨迹保留在原session，Lead日常读取简短状态和产物链接，发现问题时深入工具证据。

用户在任务对话直接调整需求时，先写入对应Issue/决策记录；Lead读取变化后只通知受影响任务，避免把整段聊天转发给全体角色。工作树/UI诊断作为单独运维任务处理。

## 项目状态放在可版本化资料中

| 载体 | 负责内容 |
| --- | --- |
| Notion | 用户需求、范围、批准与重大决策；保留版本/状态 |
| Figma | 可编辑原型和视觉/交互版本；写入锁归当前设计任务 |
| Git仓库 | 与批准版本对应的工程契约、代码、测试、任务交接与决策快照 |
| GitHub Issue/PR | 任务状态、依赖、验收条件、缺陷、评审与集成 |
| Session | 执行过程、临时探索及面向用户的讨论 |
| 本地忽略目录 | session/worktree映射、机器路径等本机信息 |

根AGENTS作为短导航；公共接口每项有唯一文件和维护者。模块局部AGENTS在代码出现后按真实边界增加。聊天中的新结论进入批准记录或版本化文件后，才成为其他任务的稳定输入。

## Lead上下文与集成管理

Lead维护简短项目状态页：当前里程碑、已批准版本、任务DAG、接口版本、风险和下一步。按里程碑开启干净的Lead session读取该页和必要决策，继续同一负责人角色。当前对话中的大量工具/UI诊断保留为历史证据。

任务状态建议：Backlog→Ready→Doing→Review→Integrated→Accepted；依赖阻塞单独标记。单任务自测和独立review通过后，按用户批准进行PR集成，再在集成基线上执行端到端回归。UI截图证明原型画面，运行时主题/计时/Hyper-V能力由实际应用测试记录支撑。

用户直接沟通入口与临时执行者分开：Lead入口持续用于需求和进度；任务session按Issue+交付物命名，用户仍可进入任一session调整。结果和需求变化通过项目记录同步，持续责任由角色与文档维持。
